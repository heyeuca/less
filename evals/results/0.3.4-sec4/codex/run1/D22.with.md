# less

Less, but better. Keep only what has a reason to exist.

## The test

For each element (sentence, caveat, heading, bullet, comment, function,
parameter, option), ask: **Does this have a clear reason to exist?**
If not, remove it. Clarity beats brevity. When unsure, keep it.
Judge what a passage does in context, not whether it matches a stock phrase.
Read the surrounding text: a qualifier may govern later sentences.
Leave sentences and code regions outside confirmed removal targets unchanged;
allow only the local repairs needed by those removals.

## When

Only on request or a clear cue, not when merely writing a draft or new code.
Remove unnecessary material; allow only the local edits needed to keep the
result grammatical or executable (such as inlining a redundant helper). No
independent style or voice rewrites, translation, fixed-length summaries,
fact-checking, algorithm substitutions, or performance work.

## Don't apply

Return the input unchanged plus one line naming the reason for:
- Legal, contractual, or other verbatim text; quotations and transcripts.
- Code, config, or commands the user didn't point at.

Change only the code the user pointed at. A user-set length or format is not
an exclusion: work inside it.

## Removal order

Check every candidate against "Never remove" first, especially the user's own
greetings and closings.

Writing:
- W1. Preamble, restated question, and greetings you added ("Great question!").
- W2. Closing recaps and offers you added, or that end a PR description, commit,
  or doc ("Hope this helps", "Want me to...").
- W3. Hedges and filler that change nothing, including sentences that could
  appear unchanged in any other document.
- W4. Duplicate points (keep the clearest).
- W5. Unrequested caveats and alternatives that don't change what the reader does.
- W6. Decoration on answers under ~5 sentences: headers, bold, bullets.
- W7. Merge and shorten the rest, keeping complete sentences: no arrows,
  fragments, or dropped articles. When editing the user's text, do not merge or
  rephrase sentences; only repair grammar directly affected by a deletion.

Code:
- S1. Comments that restate the code.
- S2. Unnecessary abstractions: helpers, wrappers, interfaces, factories.
  Single use alone is not evidence that an abstraction is unnecessary.
- S3. Unrequested options, flags, config.
- S4. Defensive code for cases that provably can't happen from the visible code.
  Otherwise keep it.

Before removing code or options, inspect available callers, exports, and
relevant tests. Preserve externally used signatures and behavior unless the
user explicitly requests that change. Run relevant existing checks after code
edits; if usage or behavior cannot be established, keep the candidate.

Documents: apply the test section by section. Keep the structure readers
navigate by: headings, TOC and anchors, numbered steps referenced elsewhere,
tables that carry data. Remove a whole section only when it fails the test.
Keep every heading and its TOC entry unless the whole section is cut; never
merge a section into the intro.

Design: for UI code the user points at, apply the test to elements and
styles. Remove only after checking [references/design.md](references/design.md)
(removal order and never-remove list). Unrequested content there means what
the agent added, not what the user wrote. Change markup and styles only; no new
aesthetic. Not for building new UI, screenshots, or Figma files.

## Never remove

- M1. Correctness: numbers, units, dates, conditions, exceptions, negations.
- M2. Claim strength: uncertainty, approximation, scope, causal relationships, and
  obligation. Keep meaning-bearing qualifiers such as "about", "some", "at
  most", "may", and "must"; shortening must not strengthen or weaken a claim.
- M3. Needed context: what the reader needs to act (prerequisites, steps, versions).
- M4. Safety: data-loss, security, money, legal, irreversible-action warnings.
- M5. The user's ask: requested content, format, length, constraints.
- M6. Attribution and citations.
- M7. The user's voice when editing their text. Don't rewrite style.
- M8. In a message to people (email, chat, letter) the user wrote: greetings,
  sign-offs, and lines asking for a reply or questions ("Let me know if...").
  E.g. "Do reach out anytime if anything is still unclear." stays; you may trim
  "anytime" and "still". Only greetings and closings are protected: other
  filler in the user's text ("basically", "literally", "just") is still cut,
  keeping their voice.
- M9. Politeness register: 존댓말/敬語 forms, 様, greetings, sign-offs. Stacked
  softeners and intensifiers inside it (정말, 혹시, 大変, 誠に, 何卒) are
  candidates only: keep them when they carry uncertainty or social intent.
- M10. Code: behavior (output, side effects, errors); error handling at real
  boundaries (I/O, network, user input); "why" comments, constraints, safety
  notes; public API and signatures unless asked; type annotations that affect
  checking or runtime; test-only hooks and seams.
- M11. Anything whose purpose you can't determine.

## Stop

Stop when every element passes the test, or when the next cut would cost
meaning or require guessing. Compare the result with the source for changed
claim strength and unintended edits to good surrounding material.
Never cut to hit a length. If the user asked to
shorten their text, filler that fails the test goes; unchanged needs a reason.

## Output

The reduced text or code only, in the same format and language. Exception:
the one-line reason under Don't apply. Don't comment on what was cut unless
the user asks; then list it. If nothing should change, return it unchanged.

# Design

For UI code (HTML/CSS, JSX/TSX, Tailwind) the agent wrote or the user points at,
and design spec or review docs (those also follow the writing and document rules).

The test comes first: does this element have a clear reason to exist for this
user's request? A signal below only nominates a candidate. Check every
candidate against "Never remove" before removing it.

Removal only: no new aesthetic, fonts, or palette. Change markup and styles
only; keep handlers, form `name`/`type`, `href`, test ids, and component APIs.

Figma files, screenshots, and other visual inputs: return them unchanged plus
one line: "less edits code or text it can return."

## Removal order

1. **R1 Decoration:** gradient washes, glows, blobs (C1); the same border,
   shadow, and radius stacked on every surface (C2).
2. **R2 Nesting:** cards in cards, wrappers with no layout job (C3).
3. **R3 Chrome:** eyebrow labels, badge pills, all-caps tracked labels (C4);
   fake 01/02/03 markers on non-sequential content (C5); icons and emoji that
   carry no meaning (C6); duplicate labels (C10); appended arrows and
   middle-dot meta strings (C11). Fixed badges or labels not tied to data or
   state (e.g. a hardcoded "New") may go; hidden state elements may not (K8).
4. **R4 Unrequested content:** sections and buttons nobody asked for (logo
   strips, testimonials, a second CTA) (C7); filler and slogan copy (C8).
   Only content the agent added; what the user wrote is theirs.
5. **R5 Motion:** entrance and hover animation that answers no user action;
   `transition: all` (C9).
6. **R6 Cleanup:** utility classes or selectors that cancel or repeat each
   other (C12).

## Signals

| ID | Signal | Looks like |
|---|---|---|
| C1 | Decorative gradient washes, blobs, glow | `bg-gradient-*`, `linear-gradient` on non-brand surfaces, `blur-3xl` orbs |
| C2 | Identical shadow and border on every surface | `shadow-*` + `border` + `rounded-*` on each card; `rgba(0,0,0,.1)` |
| C3 | Cards in cards | a card-classed element nested inside another |
| C4 | Eyebrow labels, badge pills above headings | `uppercase tracking-*` span before `h1`–`h3` |
| C5 | Fake sequence markers (01/02/03) | numbered spans in non-`ol` lists |
| C6 | Decorative icons and emoji | icon above every card title, emoji in headings |
| C7 | Unrequested sections and buttons | logo strips, testimonials, a second CTA |
| C8 | Filler copy, triads, slogans | "Empower your team…" with no specific claim |
| C9 | Scattered entrance and hover animation | per-section fade/slide-up, `transition: all`, hover on non-interactive cards |
| C10 | Duplicate labels | eyebrow repeating the heading; tooltip repeating visible text |
| C11 | Arrows and middle-dot meta as chrome | `→` on every link or button; `A · B · C` |
| C12 | Classes that cancel or repeat each other | conflicting padding/margin selectors |

## Never remove

- **K1 Accessible names:** `<label>`, `aria-label`, `alt` on meaningful
  images, visible label text (WCAG 3.3.2, 4.1.2, 2.5.3, 1.1.1).
- **K2 Semantics:** headings, landmarks, lists, tables; don't flatten them
  into `div`s (1.3.1).
- **K3 Text contrast:** 4.5:1, or 3:1 for large text, after removing any
  background or overlay (1.4.3).
- **K4 Boundaries:** a border or shadow that is a control's only ≥3:1
  indicator (1.4.11).
- **K5 Focus and target:** focus styles; no `outline: none` without a
  replacement (2.4.7). Targets stay ≥24×24 CSS px or adequately spaced (2.5.8).
- **K6 Motion opt-out:** `prefers-reduced-motion` handling. Removing the
  animation is fine; removing the opt-out isn't (2.3.3).
- **K7 Signifiers:** cues that show what is clickable; color is never the
  only cue (1.4.1).
- **K8 States:** error, empty, and loading branches, even if they look unused
  (3.3.1, 4.1.3).
- **K9 Responsive behavior:** breakpoints and media queries; reflow at 320 CSS
  px (1.4.10).
- **K10 Brand:** logo, brand tokens, required legal text.
- **K11 The user's ask:** anything requested, including sections, fields, and
  buttons.
- **K12 Overlay legibility:** on elements that sit over content (sticky or
  fixed headers, overlays, modals, drawers), a blur, shadow, or scrim that
  keeps their text readable is not decoration. If you remove it, make the
  element's background opaque (1.4.3).

K1–K12 protect the named items only, not everything near them. When unsure
whether a removal breaks one, keep it.
